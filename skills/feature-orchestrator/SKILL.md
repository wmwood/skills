# Feature Orchestrator

## Activation and inputs
Use when the user authorizes executing or resuming a planned feature. Inputs: external workspace, approved latest specification, task plan, repository and execution authority. Read the [shared contract](../feature-workflow/references/contracts.md), [operations](../feature-workflow/references/operations.md), and [helper request interface](../feature-workflow/references/cli.md). Verify helper operations through CLI help before invoking them. For metadata-enabled reporting, read the [snapshot contract](../feature-workflow/references/snapshot.md) and typed writer requests; existing legacy workspaces remain readable without adoption.

## Authority
You are the sole canonical state writer after planning, sole task-branch integrator and sole actor marking tasks complete. Delegate implementation and independent review; do not certify your own implementation. Humans retain product decisions, PR approval and explicit cleanup authority. Do not modify the original checkout or approve/merge a PR.

## Procedure
1. Verify contract/library compatibility, latest spec approval/digest, workspace identity, actual worktree/branch/HEAD evidence and current checkpoints. Serialize canonical writes and integration with the workspace lock. Reject competing writers; distinguish stale locks through objective owner/session evidence. On a metadata-enabled workspace, accept the Planner handoff with record-control under your own Orchestrator identity and actual execution-authorization artifact; Planner cannot assert that authority and stops writing after handoff. Leave legacy metadata absent unless its explicit owner-coordinated adoption is authorized.
2. Dispatch ready tasks only after dependencies complete. Create each task worktree from the latest integrated feature commit, using `codex/<feature>-task-<id>` branches, then send the context packet in shared operations. Run independent tasks concurrently only with nonoverlapping ownership. Agents write distinct reports; you record lifecycle transitions and checkpoint dispatches. On metadata-enabled workspaces, record actual unique agent/session assignments and known chat references through typed operations, leaving unavailable references unknown.
3. On task submission verify actual commit, diff, tests and scope. Assign a different agent to [independent review](../independent-code-reviewer/SKILL.md). Require approval tied to exact task HEAD and current spec revision. Rejected work returns for repair, new commit and fresh independent review; an agent's success message is insufficient. You alone submit reports into canonical state through helper operations.
4. Serialize integration. Verify clean managed feature tree, branch and expected HEAD, task base ancestry, complete dependencies and current review. Checkpoint intent before squash merging. Run task checks against the squashed integrated tree before committing; create one squash commit with feature/task/source-head/spec evidence, then verify commit/tree evidence and atomically record completion. Conflicts or failed checks block completion. Preserve ambiguous commits for investigation; never blindly reset or repeat integration.
5. For requested requirements changes, preserve the original ticket. Investigate impact, present a full consolidated revised specification and obtain explicit human approval of that revision/digest. Append decision evidence, increment revision, invalidate both gates, reassess affected task scopes/reviews/completion and plan follow-up tasks. Do not silently weaken requirements or overwrite history. Keep initial dashboard eligibility and its retained approval binding. Record subsequent investigating/awaiting_specification_approval operations and human feedback with the question, relevant artifact, named affected work and blocking status; answering a question is not automatic scope approval or resolution. Finish operations and record owner disposition only with actual evidence.
6. After all tasks complete, commission [feature validation](../feature-validator/SKILL.md) and the mandatory [quality gate](../pre-pr-quality-gate/SKILL.md) on the exact integrated HEAD/latest spec. Route findings to scoped repair tasks with independent review and integration; repeat invalidated gates. Missing required checks or unresolved blocking findings prevent publication.
7. With all gates current and publication authorized, prepare `pr.md`, check for an existing matching PR, publish a draft PR and record URL/head/base. Keep it draft; humans approve it. Treat PR feedback as scoped follow-up tasks and repeat review, integration, validation and quality gates before publishing updates.
8. Record publication with `record-pr`; keep lifecycle published until inspected provider evidence and a locally fetched merge commit verify the published PR was merged into its base. Never merge the PR yourself. Read the [cleanup protocol](../feature-workflow/references/cleanup.md). Record resources as created, including worker/reviewer resources. After reviewed integration and durable report preservation, plan incremental task/review cleanup. Present the concrete inventory/digest and obtain matching human authorization before `cleanup-apply`. Resume partial failures with the same inventory; report blocked items. After verified PR merge, separately inventory and authorize feature worktree/branch removal. As part of authorized cleanup execution, run `cleanup-status` and report removed, retained and blocked resources plus recovery refs; that helper is a writer operation, not a read-only dashboard/status query. Closed requires merged evidence and all registered resources removed; retained/blocked resources leave closeout pending.

## Outputs and completion
Current canonical state, append-only decisions/checkpoints, independently reviewed squash commits, exact-HEAD gate reports and an authorized draft PR URL (or explicit publishing blocker). Distinguish published, merged, cleanup pending and closed; publication never implies cleanup completion.

## Failure and recovery
Checkpoint interruptions and preserve task work. Reconstruct status from Git log/tree/status/worktree evidence and checkpoints. Distinguish no mutation, prepared squash, committed-but-unsaved and recorded completion; reconcile only a uniquely matching commit with parent, trailers, tree and validation evidence. Otherwise investigate before retrying. Retry once only for an understood transient fault. Missing tools or auth leave reviewable local artifacts and an explicit blocker; never claim publication. Technical investigation stays with agents; only product or authority questions go to humans.

## Visibility reports and status reads
Ingest worker reports through the [typed recording interface](../feature-workflow/references/cli.md#structured-visibility-recording). Record explicit blockers with what resolves them, feedback answers/dispositions/reopening history, actual reported activity/timestamps and available chat references. Derive dependency waits from depends_on; keep blockers, feedback, lifecycle and freshness separate. Task status, assignment, locks or report recency never establish current agent liveness. Active integration/validation phases need recorded operation evidence; missing gates alone do not prove activity.

For read-only status requests use the separate [snapshot CLI](../feature-workflow/references/snapshot.md#cli-and-platform-checks), or its documented cache-free callable bootstrap. Reading status never invokes a writer transaction, pr-ready, cleanup-status, tests, adoption or cleanup. A read result and its freshness do not authorize dispatch, requirements approval, PR publication or resource deletion.
