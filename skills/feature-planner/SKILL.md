# Feature Planner

## Activation and inputs
Use to prepare a feature for implementation. Inputs: an unstructured request, draft or prepared ticket; any existing approval evidence; repository; explicit committed baseline; and available external workspace location. Ticket Writer is optional. Read the [shared contract](../feature-workflow/references/contracts.md) and [shared operations](../feature-workflow/references/operations.md). Requires Git and Python 3.10+ for deterministic helpers; no mode switch is required.

## Authority
Investigate and interview to define scope, obtain human approval, then create the feature branch/worktree, initial external state, specification and task plan. Humans approve product behavior. A request or invocation of Planner is not scope approval. Do not implement tasks, integrate branches, mark tasks complete, approve product changes, or modify the original checkout. Planning authorization does not authorize dispatch or PR publishing.

## Procedure
1. Inspect instructions and Git state. Verify AGENTS.md and GLOSSARY.md exist and describe repository commands, architecture, ownership and terminology; route missing initialization to Repository Initializer before implementation planning. Capture original branch, HEAD, status and index evidence without stashing, cleaning or changing them.
2. Resolve scope before decomposition. For an unstructured, incomplete or unapproved request, inspect repository-answerable facts, interview the owner only on unresolved product decisions, and present one comprehensive scope draft with stable acceptance IDs, constraints and failure cases. Keep drafts, questions and investigation evidence outside repository worktrees and outside dashboard listings. Obtain explicit human approval of the exact scope and record its artifact digest/date/session evidence. Reuse a valid prepared approved ticket without repeating interview or approval; changed or contradictory scope requires approval of the affected consolidated scope before planning. Unanswered questions never imply approval. Do not produce task tickets or initialize canonical feature state/worktrees until scope approval is established.
3. Resolve an absolute external feature workspace outside all checked-out trees. Check absence of target branch/path; choose unique `codex/<feature>` naming. Prepare the isolated feature worktree destination and explicit committed baseline; the next step creates it once through init. Disclose that original uncommitted work is excluded. Never reuse existing paths on a fresh creation attempt; keep any earlier private scope-draft/handoff location separate from the new canonical workspace.
4. Prepare approved ticket/specification inputs in the separate external handoff location. Reuse the exact approved ticket content for the initial full specification unless a different full specification already has matching explicit approval evidence. Read the [helper request interface](../feature-workflow/references/cli.md) and CLI help, then invoke init once to preserve immutable `ticket.md` and `specs/0001.md`, initialize `state.json` and create the feature worktree. Do not precreate its reserved workspace/path/branch. For a new feature, supply a durable `workspace_id` to init; its visibility eligibility remains null. Preserve that identity on relocation. Record Planner control with false execution authority and actual planning-request evidence. Record partial creation in a checkpoint rather than overwriting it; partial initialization stays excluded from dashboard feature listings.
5. Decompose the approved scope into independently implementable task tickets and canonical task entries. Each records acceptance IDs, scope and excluded work, file/component ownership, interface contracts, dependencies, test commands as argument arrays, expected deliverables and baseline requirements. Validate unique IDs, present dependencies and an acyclic graph. Serialize overlapping ownership or redesign boundaries; do not dispatch competing edits. Task branches use `codex/<feature>-task-<id>` to avoid a Git ref prefix collision.
6. Cover every acceptance criterion with tasks and a feature-wide validation strategy; identify review, integration, quality gate and PR prerequisites. Keep tasks pending and runtime ownership/review/integration evidence unset. After the complete approved ticket/specification/task artifacts and dependency/coverage checks exist, invoke `publish-visibility` under Planner authority. This records initial dashboard eligibility only; it grants no PR publishing or execution authority. Earlier interviews, unanswered questions and partial plans remain private. Follow the [snapshot contract](../feature-workflow/references/snapshot.md#initial-visibility-and-retained-publication-evidence).
7. Prepare the plan and resource/context handoff. Transfer sole canonical ownership only when execution is authorized and Orchestrator accepts the handoff and records its own control/authorization evidence. Planner stops canonical writes after that acceptance; it never impersonates Orchestrator or asserts implementation authority. Existing approved planned legacy features remain readable without rerunning Planner or adopting metadata.

## Outputs and completion
An approved exact-scope ticket and approval evidence; isolated feature branch/worktree; approved initial consolidated specification; initialized external state; complete dependency-safe task tickets/acceptance coverage; initial dashboard eligibility; and a prepared dispatch handoff. Report original-checkout preservation and unresolved blockers. Planning completion is neither task completion nor execution/PR authorization.

## Failure and recovery
Missing scope approval keeps the draft and interview private and prevents decomposition/initialization. Reject unsafe paths, pre-existing creation targets, cycles or unexplained ownership collisions. Preserve partial artifacts and inspect actual worktrees/branches/state before retry; never delete or reset the original checkout. If execution authorization is missing, return the prepared plan without dispatch. Read-only status uses the separate [snapshot interface](../feature-workflow/references/snapshot.md#cli-and-platform-checks); reading never publishes eligibility, adopts metadata or invokes a writer transaction.

## Resource handoff
Transfer the schema 2 resource manifest and creation checkpoints with exact feature worktree path, branch, durable workspace identity, owner and original checkout identity. Reconcile interrupted creation before dispatch. Register additional resources under the [cleanup protocol](../feature-workflow/references/cleanup.md); planning and publication do not authorize deletion.
