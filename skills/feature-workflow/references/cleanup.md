# Cleanup protocol

## Inventory and authority

State schema 2 stores the resource manifest in `state.json.resources`. Keep feature evidence outside temporary worktrees. Before creation, checkpoint intended paths/branches/owners; immediately record actual identities, including failed or interrupted creation. Built-in worktree creation records a creating entry before Git mutation. Inspect initialization checkpoints if creation interrupts before state exists. Workers cannot edit canonical state: report creation intent/results to Orchestrator and require registration acknowledgment. Register a review worktree with purpose `review`, its task ID, and `track_attempt: true` while the matching submitted commit is under review. Register independent gate worktrees with purpose `validation` or `quality` at the integrated HEAD. Use a path separate from durable records. Finish each tracked attempt with its preserved report, including failed or superseded attempts. A failed registration is unfinished handoff work.

Use `register-resource` for additional worktrees, temporary directories, containers and networks. Exact full Docker IDs and labels `feature-workflow.feature` and `feature-workflow.owner` are required; names alone do not establish ownership. Shared resources stay retained. Use only registered resources. Temporary directories require an empty directory. For worktrees, the build record is the only basis for approving generated contents. Original checkout, application processes, ticket, specs, reports, decisions, checkpoints, state and recovery refs remain preserved.

`cleanup-plan` takes `resource_ids` and stores an exact snapshot plus `inventory_sha256`. Present the paths, exact contents, and digest for explicit human approval. `cleanup-apply` confirms that approval, rechecks the inventory and supporting evidence, and journals each item before mutation. Feature scope, publication, and cleanup each have separate authority.

## Squash integration and incremental release

A completed task and its final review require verified squash integration with exact source HEAD, recorded checks, and integration trailers reachable from `integrated_head`. A superseded review also requires its own recorded attempt and a later accepted review connected to that integration. A registered validation or quality worktree can be released after its exact attempt ends and its report and approved specification match. This does not change the current gate verdict or PR readiness.

### Build output

Use [record-build-output](cli.md#build-output-and-worktree-attempts) to run a trusted, synchronous build in the registered checkout with only the declared relative output directories in scope. The helper compares contents before and after the command. A later build can carry forward previously verified output and record newly created paths. It cannot adopt unknown files simply by moving or overwriting them. Reports and content fingerprints are kept outside the checkout. Tracked changes, index flags that could hide edits, unknown untracked or ignored data, linked paths, and unverifiable Windows data streams block cleanup.

The approved inventory records each declared directory and its verified contents. The helper validates those contents again and journals the intent for each generated entry before removing it. It removes files individually and removes eligible generated directories when empty. On POSIX, it first moves the candidate into a private, journaled quarantine under the workspace checkpoints and verifies the captured object before deleting it. The quarantine and output must be on the same filesystem, otherwise the entry stays in its original location and cleanup blocks. Unapproved content captured there is retained at the reported path. Resolve it before resuming or replacing the inventory. Ordinary Git worktree removal handles the remaining verified checkout and any approved empty scaffolding. Quiesce external writers and concurrent Git operations for the registered checkout before applying cleanup.

Before worktree or branch removal, preserve the approved commit under `refs/feature-workflow/<feature>/<resource>`. An existing preservation ref must match that exact commit. Normal Git worktree removal respects Git's safeguards. Branch deletion checks other worktrees under Git's prepared ref transaction and compares the branch and preservation ref to the approved commit. If a competing HEAD attachment is detected after a journaled branch deletion, the helper attempts to restore the approved tip only while the ref is absent and reports the block. Recovery refs remain available after cleanup.

## Publication and merge

`record-pr` records inspected provider URL/head/base/evidence after current gates pass. It performs no network calls. To record merge, first inspect the provider's merged status, matching PR identity/head/base and merge commit, fetch that commit/base through authorized normal Git operations, then supply merge_commit and the inspected service evidence. The helper checks base reachability and source ancestry or identical published/merged trees for squash/rebase. Divergent squash trees require investigation, not fabricated approval or bypassing checks. The evidence field is a cooperative assertion, not provider authentication.

Only verified merge permits feature worktree/branch deletion. Published, merged, cleanup_pending and closed are separate lifecycle states. Incremental task cleanup leaves active/published unchanged. After merge, execution enters cleanup_pending; closed requires all registered resources removed. Retained resources must be reported and leave closeout pending. Publication never implies cleanup is complete.

## Resume and closeout

Rerun `cleanup-apply` with the same approved digest after interruption. The helper skips completed items and rechecks the remaining paths. A missing output path counts as progress only after the journal records its removal intent. An absent worktree can resume branch removal only with its journaled intent and an exact preservation ref. Legacy schema-2 removal intents retain their original retry path.

Changed files or evidence keep that item blocked. Preserve unknown data and inspect what changed. A legitimately changed build needs new verified evidence before it can enter an inventory. To replace an unfinished inventory, pass its exact digest as `replaces_inventory_sha256` and include every partially removed resource. The helper archives the old inventory, progress, and approval. Remaining unchanged partial worktrees carry their journal into the replacement. An explicitly refreshed partial worktree needs a new verified snapshot and the same preserved commit. Resume interrupted directory or Docker removal before replacing its inventory. Present any replacement inventory and obtain approval for its new digest.

Containers must be stopped and networks must have no attached containers. Docker retry proves absence through successful exact-ID listing. Preserve a stale lock until objective owner/session evidence permits deliberate takeover.

`cleanup-status` reports removed, retained, blocked and always-preserved evidence; inspect blocked entries even when the CLI exits successfully. Resolve unknown or changed resources explicitly; never force through a failed preflight. Run status after execution and include exact IDs/paths/branches, recovery refs and reasons in the closeout report. Use Git history for completed feature documentation; keep only reusable development conventions in repository instructions.
